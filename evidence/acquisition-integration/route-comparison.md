## Decision

**Recommended next implementation: one minimal native iOS measurement-mode recorder plus the backend Float32/manifest boundary.** Keep phyphox as the currently available provisional route until the new recorder is installed and qualified. Defer the browser recorder: its desktop software checks are useful, but its phone deployment adds a secure-origin decision and its graph timestamps provide weaker device-route evidence. We should not build both routes.

This recommendation was updated after checking the actual installed SDK and successfully typechecking the required native APIs for an unsigned arm64 iOS17 target. No microphone, signing credentials, device, network deployment or global configuration was involved. Native implementation is modestly more packaging work than an unstyled browser page, but closes the relevant phone route/session metadata gap directly. A local unsigned app can be compiled and inspected now; it cannot be installed on a normal iPhone as-is. Later signing/install and physical qualification remain explicit unresolved steps, not implied completion.

The common useful change is a delivered-Float32 recording/import contract with timestamp and interruption metadata. It preserves existing phyphox import and can later accept browser-delivered samples without equating either route with raw ADC. Native compile success plus deterministic collector/export tests is the strongest demonstrably available software milestone under the present authority; no physical recording claim follows.

## Current route and reproducible gap

`examples/echosight_audio_capture.phyphox` requests48kHz, appends samples, exports `sample_value` and `reported_rate_Hz`, and contains no per-buffer timestamps, interruption events or route snapshots. The importer preserves the original ZIP, rejects explicit missing rows, and diagnoses its unverifiable sample grid. Its actual phone export remains untested. Official input documentation confirms append and rate outputs; requested iOS rate is a preference. [phyphox input](https://phyphox.org/docs/file-format/input/)

The backend's `_read_wav` accepts integer mono PCM only. A six-value SciPy-generated Float32 WAV was rejected with `ValueError: invalid PCM WAV`. Conversion to PCM32 changed the finite delivered value2^-35 into zero. Float32-to-Float64 widening and conversion back preserved all selected Float32 bit patterns, including negative zero. Node DataView little-endian Float32 serialization also preserved the selected finite values and negative zero. These are executed software checks, not ADC measurements or evidence that quantization is presently the dominant spatial error.

Reproduction (project Python): create `samples=np.array([0.,-0.,2**-35,.125,.12345678,-.9876543],np.float32)`; write through `scipy.io.wavfile.write(BytesIO(),48000,samples)`; pass to `echosight.storage._read_wav`. Compare `samples.astype(float)` with `rint(samples.astype(float)*2**31)/2**31`. Exactly one of these six selected numerical values changes. The test establishes that an unconditional “lossless delivered Float32 through integer PCM32” claim would be wrong, not that every practical microphone sample loses meaningful accuracy.

| Raw ADC or guaranteed no processing | Not established | Not established | Not established by measurement mode alone |
| Immediate useful result without phones | Existing import tests | Exact serialization, local graph assembly, interruption/rejection tests | Compilation and pure serialization/state-machine tests |

Browser facts: AudioWorklet operates on delivered Float32 graph samples. `currentFrame` and `sampleRate` describe that graph, not an independently calibrated ADC clock. The specification requires resampling when a MediaStream track and its AudioContext have different rates. Logging both rates exposes a mismatch; equality does not prove no earlier conversion. Use the2021 Recommendation for stable behavior; the current1.1 page is a2024 First Public Working Draft. [Web Audio Recommendation](https://www.w3.org/TR/2021/REC-webaudio-20210617/) [Current draft](https://www.w3.org/TR/webaudio/)

Request echo cancellation, gain control and noise suppression off, but record requested constraints, supported constraints, capabilities and actual settings separately. Unsupported or omitted settings remain unknown. Track mute/ended and context suspension must invalidate a shot; a muted track can deliver silence, so graph-frame continuity alone cannot prove uninterrupted microphone acquisition. [Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/)

Localhost's trust exception applies to loopback on the device running the browser. A phone visiting the MacBook's plain LAN address does not become localhost. No certificate, tunnel, public deployment or origin-security bypass is proposed. [Secure Contexts](https://www.w3.org/TR/secure-contexts/)

Native facts: installed iPhoneOS27 SDK `AVAudioSessionTypes.h` documents measurement mode as reducing system processing, including disabling some dynamics processing; it does not promise unprocessed ADC output. `AVAudioTime.h` separately exposes validity for sample and host time. Apple's preference guidance requires reading actual values after session activation rather than treating preferred rate/buffer duration as guaranteed. [Apple preference guidance](https://developer.apple.com/library/archive/qa/qa1631/_index.html) The measurement web page was accessible but exposed only a JavaScript shell, so the active local SDK headers supplied the detailed evidence. [Apple measurement entry](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/measurement)

## Precise bounded implementation proposal

1. Add strict mono IEEE Float32 WAV import (format3,32bits) preserving original bytes and exact finite delivered values when widened for computation. Validate format, declared/actual byte counts, sample count, duration/rate caps and finite data. Do not silently clip amplitudes or quantize to integer PCM. Keep existing PCM/phyphox behavior. A raw `.f32le` plus manifest is an alternative if WAV parsing costs more complexity, but choose one authoritative representation, not both.
2. Define a versioned acquisition manifest bound to recording SHA-256. Fields: recorder/version; data layer=`webaudio_delivered_float32`; graph rate; reported track rate or unknown; requested and observed processing settings; selected input-track/channel identity; supplied source route/configuration and probe hash; per-block sequence, first graph frame and frame count; start/stop reason; interruption events; continuity verdict; sample count and dropped/duplicate-block counts. Appending samples after a suspend/restart creates a rejected shot, not a silently contiguous recording. Browser event times are observations, not exact microphone transition timestamps.
3. Implement one unstyled local page with Start, Stop and Export, no viewer/dashboard/upload integration. Use one input channel explicitly without hidden averaging, a bounded preallocated worklet capture buffer, actual block lengths, and a maximum20-second shot. Stop on buffer overflow, missing channel, processor failure, track interruption, context suspension or route/settings change. Transfer Float32 chunks without compression; keep first/last graph frames and sequence numbers. Avoid a SharedArrayBuffer requirement so cross-origin isolation is unnecessary. Drain and acknowledge the final block before export; retain a rejected partial recording with its reason.
4. Verify the recorder in a local trusted desktop context using an OfflineAudioContext or controlled synthetic graph, not a microphone. Separate pure collector/encoder tests from actual browser AudioWorklet tests. Node stubs alone must not be labeled browser execution.
5. Extend backend import of the paired manifest only after format/state tests pass. Manifest claims remain recorder-supplied evidence; a hash binds bytes but does not authenticate hardware. CLI import can come before HTTP upload; current API rejects browser Origin requests, so no implicit CORS weakening.

Software acceptance is predeclared: exact byte/value round trip for deterministic positive/negative/zero/subnormal samples; exact sample counts for non-multiple block lengths and final partial block; rejection of missing/duplicate/out-of-order graph blocks; rejection of suspension/resume, mute/end, channel change and overflow; bounded memory and malformed/truncated files; manifest checksum mismatch; preservation through backend import/export/reload. A generated probe traversing the recorder graph and import must match the delivered graph samples, not the source's pre-resampling buffer. The numerical pipeline must consume this import path. End-to-end microphone fidelity, hidden OS processing, real interruptions, graph-to-physical clock calibration and actual phone delivery remain later hardware gates.

## Selected native implementation scope and contract proposal

Create `acquisition/ios/` containing a small UIKit app with only Start, Stop, Export and status; a recording engine; a platform-independent bounded collector/exporter; an Info.plist declaring microphone usage; a minimal Xcode project and unsigned local build instructions. No dashboard, charts, playback, networking, accounts or background-recording promise. Use AVAudioSession category `.record`, mode `.measurement`, a48kHz preference and actual post-activation format; request permission only after an explicit Start action. Capture one channel explicitly from the selected input format without averaging; if the hardware cannot provide the declared channel route, reject rather than silently change it. No voice-processing audio unit should be selected by the harness.

Capture exact Float32 values from delivered AVAudioPCMBuffer frames into a bounded20-second collector. Export IEEE Float32 WAV and one hash-bound JSON manifest. Use the input-node format actually installed on the tap; record both that format and AVAudioSession's activated sample rate. Preserve bytes and flag nonfinite samples, missing/duplicate sampleTime intervals, rate/channel changes, buffer overrun, user interruption, session interruption, engine configuration change, media-services loss/reset and route change. Stop and retain a rejected partial shot; never concatenate a resumed route into one supposedly continuous shot. No resampling or gain normalization is added by our code, but OS/device processing remains unqualified.

Proposed shared fields for coordinator agreement before coding: `schema_version`, `capture_id`, `recording_sha256`, `sample_encoding: ieee_float32_le`, `sample_rate_hz`, `channel_count`, `frame_count`, `recorder` name/version, `acquisition_layer: ios_audioengine_delivered_buffers`, supplied source route/configuration/probe identity, initial/final route snapshots, and `continuity` containing status/reasons plus per-block sequence, accumulated first-frame index, actual frame count, sampleTime validity/value and hostTime validity/value. Preserve Mach host ticks as decimal strings if needed to avoid JavaScript integer precision loss, with the timebase numerator/denominator. Event metadata records observation time and original reason; it is not an exact bound on when a microphone discontinuity began. Recorder-declared continuity remains untrusted evidence, not authentication.

Implement the collector independently of AVAudioEngine so deterministic injected buffers/timestamps can test exact values, final partial blocks, bounds and all interruption/error transitions without starting a microphone. The tap-to-collector handoff must use bounded buffering and explicitly reject overrun; callback/main-thread ownership must be reviewed so stopping/export cannot race a final buffer. Unit tests need not pretend to exercise iOS interruption delivery. Build the iPhone target with `CODE_SIGNING_ALLOWED=NO`, a project-local derived-data path and generic iOS destination. Inspect the resulting executable/app metadata; do not sign, deploy or launch it on a device. SDK/typechecking is available, but full application build has not yet been attempted.

Estimated relative effort, not a deadline: native engine/collector/event capture and minimal UI are comparable in source size to worklet/collector/event capture plus a browser page. Native adds a small Xcode target and subsequent signing/install requirement; browser adds phone HTTPS hosting/trust and retains less route introspection. Float32 import and manifest validation are required by either. Existing native SDK availability makes native the narrower route for this project's phone requirements.

The current browser design above remains a comparison, not a second implementation assignment. Do not spend effort on phone HTTPS, certificates or an alternative deployment while the native software checks can progress. Root can own backend Float32/manifest import while this agent owns the native harness once the shared contract is agreed. Physical phone testing, hidden OS processing and source calibration remain later gates.
